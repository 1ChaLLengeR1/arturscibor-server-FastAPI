## Zakres zmieniony względem pierwotnego planu

Stary model trzymał dokładnie jedno zdjęcie na tool bezpośrednio w kolumnach
(`path_image`, `link_image`). Nowy wymóg: **0..N zdjęć na tool**, przez
generyczny magazyn plików z [`docs/6-file-storage-section-done.md`](6-file-storage-section-done.md)
zamiast własnej logiki zapisu na dysk.

| Endpoint | Auth | Uwaga |
|---|---|---|
| `GET /api/v1/tools/collection` | brak (publiczny) | lista wszystkich toolów, sortowana `numeric ASC` (kolejność wyświetlania), każdy z listą podpiętych obrazów |
| `POST /api/v1/admin/tools/create` | admin | tworzy tylko rekord tekstowy — bez zdjęć |
| `PUT /api/v1/admin/tools/{tool_id}/update` | admin | częściowy update (`exclude_unset`) |
| `DELETE /api/v1/admin/tools/{tool_id}/delete` | admin | kasuje tool + wszystkie podpięte pliki (DB+dysk) |
| `POST /api/v1/admin/tools/{tool_id}/images` | admin | podpina potwierdzony (`CONFIRMED`) plik pod tool |
| `DELETE /api/v1/admin/tools/{tool_id}/images/{file_id}` | admin | odpina = w pełni kasuje plik (DB+dysk) |

Brak "get one" — jak w contact, niepotrzebne przy tak małej, w całości
publicznie widocznej kolekcji.

## Model `Tools` — zmieniony

Usunięte: `path_image`, `link_image` (zastąpione przez `files` +
`tools_images`). Dodane: `created_at`/`updated_at` (`server_default=func.now()`,
wzorem `Contact`). Naprawiony typ: `progress`/`numeric` były `String` mimo
że i tak zawsze były liczbami (stary kod rzutował `numeric: int = Form()`)
— teraz `Integer`. `progress` to poziom umiejętności w % (walidacja `0-100`
w schemacie), `numeric` to kolejność wyświetlania na liście.

## Nowa tabela `tools_images` — łącznik z generycznym `files`

Rozważone dwie opcje: FK bezpośrednio na `File` (`files.tool_id`) vs. osobna
tabela łącznikowa. Wybrana **druga** — `File` zostaje domenowo-neutralny
(współdzielony też przez przyszłe `projects`/`aboutme`, patrz
`docs/6-file-storage-section-done.md`), zamiast dokładać kolejną nullable
kolumnę FK na każdą kolejną migrowaną domenę. To dokładnie wzorzec, który
projekt już miał w starym schemacie (`ImagesProjects.id_project →
Projects.id`), tylko `file_id` wskazuje teraz na współdzielony rekord w
`files` zamiast duplikować `path`/`link`.

```
tools_images: id, tool_id → tools.id (ON DELETE CASCADE),
               file_id → files.id UNIQUE (ON DELETE CASCADE), sort_order, created_at
```

`UNIQUE(file_id)` — jeden plik należy do co najwyżej jednego toola.

**Flow podpięcia:** `POST /admin/file/init` → `PUT .../upload` → `PATCH
.../confirm` (istniejący mechanizm, `directory="projects"`... tu:
`directory="tools"`) → `POST /admin/tools/{tool_id}/images {file_id}`.
Podpięcie wymaga `file.status == CONFIRMED` — to właśnie dlatego confirm
istnieje: plik niepotwierdzony nie może zostać nigdzie przypięty.

**Kasowanie — ustalone z Tobą wprost (oba: pełne, nie soft-unlink):**
- Odpięcie pojedynczego zdjęcia (`DELETE .../images/{file_id}`) woła
  `handler_delete_file` z generycznej domeny `file` — kasuje rekord `files`
  i bajty z dysku. `ON DELETE CASCADE` na `tools_images.file_id` sprząta
  wiersz łącznika przy okazji, bez osobnego kroku.
- Kasowanie całego toola najpierw iteruje po podpiętych plikach i kasuje
  każdy przez `handler_delete_file`, dopiero potem kasuje wiersz `tools`.
  `tools_images.tool_id ON DELETE CASCADE` to tylko backstop na wypadek
  ręcznej ingerencji w DB — normalna ścieżka nigdy na niego nie liczy.

## Znane, świadomie nierozwiązane gapy

- Brak rate limitingu (jak w `contact` i `file` — `slowapi` świadomie
  pominięte, patrz `docs/6-file-storage-section-done.md` pkt. 8).
- `sort_order` w `tools_images` jest ustawiany tylko przy attach
  (kolejność dodania) — nie ma jeszcze endpointu do jego zmiany
  (przeciąganie/reorder zdjęć). Kolumna czeka gotowa.
