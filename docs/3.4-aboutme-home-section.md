> Plan przepisany od zera (ustalone z Arturem) — **nie** 1:1 migracja starych
> tabel. Stary model (`AboutMe.path_image`/`link_image`, `Information`
> jako duplikat `AboutMe.information`, `ReadMore` jako płaska lista,
> `Jobs` jako sam string) zastąpiony markdownem + generycznym magazynem
> plików z [`docs/6-file-storage-section-done.md`](6-file-storage-section-done.md),
> dokładnie wzorem [`docs/3.3-tools-section-done.md`](3.3-tools-section-done.md).
> `work` zaprojektowane w stylu LinkedIn "Doświadczenie" — firma → wiele
> stanowisk pod firmą (patrz pkt. 4.2).
>
> **Wielojęzyczność wbudowana od razu, nie doklejona później** — patrz
> [`docs/7-i18n-section.md`](7-i18n-section.md). `AboutMe.job_title`/
> `body_markdown` i `WorkItem.title`/`location`/`body_markdown` poniżej
> (pkt. 4.1, 4.2) w praktyce mają typ `JSONB`
> (`{"pl": "...", "en": "..."}`, `docs/7` pkt. 7), nie `String` jak
> pokazano w przykładach kodu niżej — traktuj pola markdown/tekstowe
> poniżej jako "co jest tłumaczalne", nie jako finalny typ kolumny.

## 1. Cel

Dwie sekcje treściowe portfolio:

1. **`aboutme`** — singleton "o mnie": krótkie pola (imię, tytuł) + długi
   markdown (zastępuje `information` + `ReadMore`) + karuzela zdjęć.
2. **`work`** — "Doświadczenie" w stylu LinkedIn: firma (`Work`) →
   wiele stanowisk pod nią (`WorkItem`), każde z własnym opisem-markdown,
   typem zatrudnienia, datami i tagami umiejętności. Firma ma **opcjonalne
   jedno logo**, nie karuzelę.

Plus przy okazji: **CV** (PDF) przepięte pod generyczny magazyn plików
zamiast własnej, osobnej ścieżki zapisu.

## 2. Markdown — jak GitHub renderuje README

Backend **nie** parsuje ani nie renderuje markdownu — trzyma surowy tekst
(`Mapped[str]`, `String` bez limitu wystarczy w Postgres), zwraca go w
JSON. Całe renderowanie (nagłówki, listy, pogrubienia, linki) dzieje się
po stronie Vue jakąś biblioteką typu `markdown-it` / `marked` (frontend,
poza zakresem tego repo). Jedyna rzecz po stronie backendu: rozsądny
`max_length` w payloadzie (Pydantic `Field`), jak przy `Contact.description`
czy `Tools.information`.

Sanityzacja pod XSS to zadanie frontendu (np. `DOMPurify`, jeśli kiedyś
dopuścisz surowe HTML w markdownie) — przy jednym adminie z dostępem do
edycji ryzyko praktycznie żadne (self-XSS), ale warto to mieć z tyłu głowy.

## 3. Dwa wzorce podpięcia plików — nie mylić

**(A) Karuzela 0..N** (`aboutme` — realnie może mieć więcej niż jedno
zdjęcie): dokładnie wzorzec `tools_images` (sprawdzony, złapał tam realny
bug — patrz `docs/3.3-tools-section-done.md`). Mała tabela łącznikowa,
`file_id UNIQUE`, `ON DELETE CASCADE` w obie strony, `sort_order`. Flow:
`init → upload → confirm` → `POST .../images {file_id}` (wymaga
`CONFIRMED`). Odpięcie = pełne skasowanie pliku przez `handler_delete_file`.

**(B) Pojedynczy opcjonalny plik 0..1** (logo firmy w `work`, CV): **bez**
osobnej tabeli — zwykły nullable `file_id` FK bezpośrednio na encji
(`Work.logo_file_id`, `CurriculumVitae.file_id`). Upload = **podmiana**:
jeśli stary plik istniał, kasowany przez `handler_delete_file`, potem
podpinany nowy. Prostsze niż (A), bo nigdy nie ma więcej niż jeden plik do
ogarnięcia — nie potrzeba `sort_order` ani osobnej tabeli.

## 4. Model danych

**Konwencja timestampów (ustalone):** tabele z realną, edytowalną treścią
dostają `created_at` + `updated_at`. Czyste tabele-łączniki (jak
`about_me_images` — insert/delete, nigdy update) dostają tylko
`created_at`.

### 4.1 `database/psql/models/aboutme.py` (przepisany)

```python
class AboutMe(Base):
    __tablename__ = "about_me"

    id: Mapped[uuid.UUID] = mapped_column(Uuid, primary_key=True, default=uuid.uuid4)
    name: Mapped[str | None] = mapped_column(String)
    job_title: Mapped[str | None] = mapped_column(String)   # krótka linijka, np. "Backend Developer"
    body_markdown: Mapped[str | None] = mapped_column(String)  # długi tekst — zastępuje information + ReadMore
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now())


class AboutMeImage(Base):
    __tablename__ = "about_me_images"

    id: Mapped[uuid.UUID] = mapped_column(Uuid, primary_key=True, default=uuid.uuid4)
    about_me_id: Mapped[uuid.UUID] = mapped_column(Uuid, ForeignKey("about_me.id", ondelete="CASCADE"))
    file_id: Mapped[uuid.UUID] = mapped_column(Uuid, ForeignKey("files.id", ondelete="CASCADE"), unique=True)
    sort_order: Mapped[int] = mapped_column(Integer, default=0, server_default="0")
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())  # łącznik — tylko created_at
```

**Singleton** — dokładnie jeden wiersz `about_me`, wstawiany przez migrację
(seed). Bez endpointu `create`/`delete` — tylko `get` (publiczny) i
`update` (admin).

### 4.2 `database/psql/models/work.py` (nowy plik, zastępuje `home.py:Jobs`)

Dwupoziomowo, jak LinkedIn "Doświadczenie": firma → N stanowisk.

```python
class EmploymentType(enum.StrEnum):
    FULL_TIME = "full_time"        # Pełny etat
    PART_TIME = "part_time"        # Niepełny etat
    CONTRACT = "contract"          # Umowa zlecenie / freelancing
    B2B = "b2b"
    INTERNSHIP = "internship"      # Staż / praktyka
    VOLUNTEER = "volunteer"        # Wolontariat


class Work(Base):
    """Firma. Logo opcjonalne, pojedyncze (wzorzec B z pkt. 3) — nie karuzela."""

    __tablename__ = "work"

    id: Mapped[uuid.UUID] = mapped_column(Uuid, primary_key=True, default=uuid.uuid4)
    company_name: Mapped[str] = mapped_column(String)
    logo_file_id: Mapped[uuid.UUID | None] = mapped_column(Uuid, ForeignKey("files.id", ondelete="SET NULL"))
    numeric: Mapped[int | None] = mapped_column(Integer)  # kolejność firm, wzorem Tools.numeric
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now())


class WorkItem(Base):
    """Stanowisko pod firmą. `date_to = NULL` = obecnie (trwające)."""

    __tablename__ = "work_items"

    id: Mapped[uuid.UUID] = mapped_column(Uuid, primary_key=True, default=uuid.uuid4)
    work_id: Mapped[uuid.UUID] = mapped_column(Uuid, ForeignKey("work.id", ondelete="CASCADE"))
    title: Mapped[str] = mapped_column(String)                      # np. "Software Engineer"
    employment_type: Mapped[EmploymentType | None] = mapped_column(Enum(EmploymentType, name="employment_type"))
    location: Mapped[str | None] = mapped_column(String)            # np. "Wrocław, Polska" / "Zdalnie"
    date_from: Mapped[date | None] = mapped_column(Date)
    date_to: Mapped[date | None] = mapped_column(Date)               # NULL = obecnie
    body_markdown: Mapped[str | None] = mapped_column(String)
    skills: Mapped[list[str] | None] = mapped_column(ARRAY(String))  # Postgres ARRAY — projekt i tak jest Postgres-only
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now())
```

**Sortowanie:** `Work` po `numeric ASC` (jak `Tools`). `WorkItem` w obrębie
firmy po `date_from DESC` — automatycznie, bez osobnego pola kolejności;
stanowisko z najpóźniejszą datą startu (typowo: obecne, `date_to IS NULL`)
wypływa na górę, dokładnie jak na LinkedIn.

**Bez karuzeli/`WorkItemImage`** — zdjęcia są tylko na poziomie firmy
(`Work.logo_file_id`), nie per-stanowisko (patrz screen LinkedIn: logo raz
przy firmie, nie przy każdej pozycji).

**`skills` jako Postgres `ARRAY(String)`, nie osobna tabela** — świadomie
najprostsza opcja: bez potrzeby efektywnego wyszukiwania "wszystkie pozycje
z tagiem X" po stronie SQL (to jednoosobowe portfolio, nie wyszukiwarka
ofert pracy), kolumna wystarczy. Gdyby to się zmieniło — łatwo dogonić
osobną tabelą `skills`+join później.

### 4.3 `database/psql/models/file.py` — rozszerzenie

```python
class FileType(enum.StrEnum):
    PHOTO = "photo"
    VIDEO = "video"
    DOCUMENT = "document"   # nowość — CV

ALLOWED_EXTENSIONS = {
    FileType.PHOTO: {".jpg", ".jpeg", ".png", ".webp"},
    FileType.VIDEO: {".mp4", ".mov", ".avi", ".mkv", ".webm", ".m4v"},
    FileType.DOCUMENT: {".pdf"},
}

ALLOWED_DIRECTORIES = {"projects", "aboutme", "tools", "work", "cv"}
```

`work` jako katalog obsługuje i logo firm, i (gdyby kiedyś potrzebne) inne
pliki tej domeny — jeden katalog na całą domenę, tak jak w `tools`.

### 4.4 `database/psql/models/home.py` → `cv.py` (przemianowany, tylko CV zostaje)

`Jobs` i `ImagesMe` znikają (zastąpione przez `Work`/`WorkItem` i logo
per firma — nie ma już potrzeby osobnej, niepowiązanej z niczym galerii
`imagesme`).

```python
class CurriculumVitae(Base):
    __tablename__ = "curriculum_vitae"

    id: Mapped[uuid.UUID] = mapped_column(Uuid, primary_key=True, default=uuid.uuid4)
    file_id: Mapped[uuid.UUID | None] = mapped_column(Uuid, ForeignKey("files.id", ondelete="SET NULL"))
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now())
```

Singleton (seed przez migrację, `file_id` startowo `NULL`), wzorzec (B) z
pkt. 3 — upload CV = podmiana starego pliku. `ON DELETE SET NULL` (nie
CASCADE) — gdyby plik zniknął z innego powodu, CV nie kasuje się razem z
nim, tylko traci referencję.

## 5. Endpointy

| Endpoint | Metoda | Auth | Uwaga |
|---|---|---|---|
| `/api/v1/aboutme` | GET | publiczny | singleton, z listą zdjęć |
| `/api/v1/admin/aboutme/update` | PUT | admin | częściowy update (`exclude_unset`, wzorem `tools`) |
| `/api/v1/admin/aboutme/images` | POST | admin | attach (wymaga `CONFIRMED`) |
| `/api/v1/admin/aboutme/images/{file_id}` | DELETE | admin | detach = pełne skasowanie pliku |
| `/api/v1/work/collection` | GET | publiczny | lista firm (`numeric ASC`), każda z zagnieżdżonymi `items` (`date_from DESC`) i `logo_url` |
| `/api/v1/admin/work/create` | POST | admin | tworzy firmę (bez stanowisk) |
| `/api/v1/admin/work/{work_id}/update` | PUT | admin | częściowy update (`company_name`, `numeric`) |
| `/api/v1/admin/work/{work_id}/delete` | DELETE | admin | kasuje firmę + logo + wszystkie stanowiska (cascade) |
| `/api/v1/admin/work/{work_id}/logo` | PUT | admin | podmienia logo (wzorzec B) |
| `/api/v1/admin/work/{work_id}/logo` | DELETE | admin | usuwa logo (bez usuwania firmy) |
| `/api/v1/admin/work/{work_id}/items` | POST | admin | dodaje stanowisko pod firmą |
| `/api/v1/admin/work/{work_id}/items/{item_id}/update` | PUT | admin | częściowy update stanowiska |
| `/api/v1/admin/work/{work_id}/items/{item_id}/delete` | DELETE | admin | kasuje stanowisko |
| `/api/v1/cv` | GET | publiczny | metadane aktualnego CV (`null`, jeśli nie wgrano) |
| `/api/v1/admin/cv/upload` | PUT | admin | podmienia CV (wzorzec B) |

Brak `download-cv` jako osobnego endpointu ze starego kodu (skanowanie
katalogu + ręczny `FileResponse`) — `/static` już serwuje plik pod jego
`url`, frontend linkuje bezpośrednio (`<a :href="cv.url" download>`).

## 6. Struktura plików (wzorem `tools`)

- `database/psql/models/{aboutme,work,file,cv}.py`
- `core/repository/psql/aboutme/{response,one,update}.py` +
  `core/repository/psql/aboutme/images/{attach,one}.py` (wzorzec A)
- `core/repository/psql/work/{response,create,one,collection,update,delete}.py`
  (firma) + `core/repository/psql/work/logo/{update,delete}.py` (wzorzec B)
  + `core/repository/psql/work/items/{create,update,delete}.py` (stanowiska)
- `core/repository/psql/cv/{response,one,update}.py` (wzorzec B)
- `core/handler/{aboutme,work,cv}/...` — `delete`/podmiana pliku
  orkiestrują kasowanie przez `core/handler/file/delete.py`
  (cross-domain, jak w `tools`)
- `api/schemas/{aboutme,work,cv}/`
- `api/endpoints/{aboutme,work,cv}/...` (publiczne) +
  `api/endpoints/admin/{aboutme,work,cv}/...` (admin, w tym
  `api/endpoints/admin/work/items/` jako sub-resource)
- `api/router.py`, `api/endpoints/urls.py` — zarejestrowane
- Migracja: `DROP TABLE informationme, readmore, jobs, imagesme`,
  `CREATE TABLE about_me, about_me_images, work, work_items,
  curriculum_vitae` (+ seed po jednym wierszu `about_me`/`curriculum_vitae`),
  `ALTER TYPE file_type ADD VALUE 'document'`, `CREATE TYPE employment_type`
  + rozszerzenie `ALLOWED_EXTENSIONS`/`ALLOWED_DIRECTORIES`

Stary `routers/AboutMe/`, `routers/Home/` — do skasowania po migracji
(jak `routers/Tools/`).

## 7. Utracone dane / świadome uproszczenia

- `ReadMore` (nazwa+tekst+kolejność) znika bez migracji danych do nowego
  `body_markdown` — jeśli tam jest coś, na czym Ci zależy, warto to ręcznie
  przepisać na markdown przy okazji edycji po migracji, nie automatycznie.
- `ImagesMe` (dzisiejsza galeria portfolio) znika jako osobny byt — zdjęcia
  które tam są, jeśli mają zostać, trzeba będzie ręcznie wgrać ponownie
  przez `aboutme` (jedyne miejsce z realną karuzelą w tej sekcji).
- `Jobs` (płaskie stringi) nie migruje się automatycznie do `Work`/`WorkItem`
  — nowy model ma dużo więcej pól (firma, stanowisko, daty, markdown,
  typ zatrudnienia, umiejętności), więc to nie jest mechaniczne 1:1
  przeniesienie danych.

## 8. Otwarte pytania (mniejsze, nie blokują startu)

1. `max_length` dla `body_markdown` (`AboutMe`, `WorkItem`) — propozycja:
   20 000 znaków (spory margines na długi markdown, ale nie nielimitowany).
2. `EmploymentType` — lista w pkt. 4.2 to propozycja startowa (6 wartości)
   — do potwierdzenia czy kompletna, czy czegoś brakuje.
3. Rate limiting — jak zawsze, pominięty (osobny branch).
